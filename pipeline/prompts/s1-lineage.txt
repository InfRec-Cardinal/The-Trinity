# Stage 1 - Audit provenance across the admitted library

Audit the provenance of the admitted task library. Every task has passed specification review, but a task-local statement that resources are not shared does not prove it is independent of the other tasks. Build one canonical registry for the entire admitted task library before the host selects unseen tasks. Consider every direction and both protocol kinds together.

Search and inspect original sources when the supplied evidence is insufficient. Public benchmark material, competition organizer/author material, forum task/result posts and their linked implementations can all contribute, alongside documentation, repositories, data/resource descriptions and dependency evidence. Attribute claims correctly and investigate original resources rather than assuming a forum result proves provenance. Use `fetch_page` to capture a source and `read_page` to inspect it. Quotes must be verbatim from captured pages. Investigate missing lineage information within the available tool budget and report any unresolved evidence gaps. Search summaries and plausible assumptions are not evidence.

Inventory concrete transferable resources used by each task: its task-specific engine or environment, worlds and assets, datasets and generation corpora, repository implementation, protocol and task variants. Include resources whether or not a second task currently uses them. A generic programming language or ubiquitous utility library alone does not establish shared task lineage. Include all resources already declared in the specifications, including `sharedResources`.

Resolve alternate names, abbreviated identifiers, forks, mirrors, redirects, renamed repositories and different URLs of the same artifact. Give each concrete resource one stable kebab-case id, a clear name and kind, all observed aliases and URLs, and captured evidence establishing its identity and relationship to the tasks. Include the original specification resource ids in aliases when canonical ids differ. Do not create separate canonical resources for two names of the same artifact. Do not merge distinct resources merely because they share a generic label.

Audit every task exactly once and list its canonical `resourceIds`. Compare inventories across the whole library, including static benchmarks; directions do not protect against leakage. Set `comparedLibraryFingerprint` to the exact fingerprint supplied in the kickoff to confirm that you compared the entire current library. You may then omit per-task `consideredTaskIds`; the host records the complete comparison scope. Alternatively, each task must list every other admitted task in `consideredTaskIds`. Do not repeat all peer ids for every task when the fingerprint declaration can express the same scope.

- `shared`: captured evidence or canonical-resource identity establishes overlap with another admitted task.
- `independent`: a nonempty, evidenced inventory has been compared against every other admitted task's evidenced inventory and no transferable task resource overlaps. Explain the identity and version distinctions that support this conclusion. Do not infer independence from different task titles, source URLs, root categories or an empty shared-resource list.
- `unknown`: relevant resources, aliases, dependencies or a peer inventory remain unresolved after investigation. State precisely what is missing. Never treat the absence of documented overlap as evidence of independence.

Every resource requires evidence. Every `independent` or `shared` task verdict requires evidence and a nonempty inventory. When a peer's inventory is unknown, you cannot exclude overlap with it: resolve the peer or keep the affected verdict unknown. Newly authored tasks cannot become unseen even if their provenance is known.

Save the audit incrementally rather than generating the whole library in one response. Keep each submission within the response output limit. If a call is truncated, resubmit a smaller complete batch; an empty object or continuation fragment cannot be executed.

1. Start with `read_lineage_draft` using `section: "status"`. It reports saved canonical ids and missing task ids. This durable draft survives stopping, provider-quota failures and agent budget extensions. Reuse saved rows; do not reconstruct or resubmit them unless correcting a specific field or canonical identity. The kickoff is stable across resumes; the saved draft's status is the current progress.
2. Register evidenced resources with `stage_lineage_resources`. Send at most 12 total resource rows and obsolete-id removals in one call, and only one staging call per model reply. Keep the entire call below 24,000 UTF-8 bytes; choose a smaller batch when rows need more evidence. Prefer concise names, a short public justification and the minimum quotations that establish the claims. This limit bounds output size, not audit coverage. You may interleave resource and task batches, but stage every resource before a task references it.
3. Save task verdicts with `stage_lineage_tasks`, at most 12 tasks in one call and only one staging call per model reply. Set `comparedLibraryFingerprint` on every staging call. Omit per-task `consideredTaskIds` when confirming the complete comparison scope through that fingerprint. Each saved task still needs its full inventory and required captured evidence. Staging checks quotations and declared resources immediately; it does not approve independence. Revisit provisional verdicts after comparing all peer inventories.
4. To merge aliases discovered later, stage the surviving canonical resource with all aliases and use `removeResourceIds` for the obsolete ids in the same resource call. Then update affected task rows to the surviving id. Replacement uses resource id or task id, so corrections do not add duplicate rows. `read_lineage_draft` can page through saved `resources` or `tasks`, with a limit of at most 12 rows.
5. Once every task has been staged and the entire library has been compared, call `submit_lineage_audit` with only `comparedLibraryFingerprint` and `finalize: true`. Do not repeat the resources or task arrays. The host assembles the durable draft and checks the complete library: exactly-once coverage, captured quotations, all declared resources, aliases, URL overlap, and unresolved peer inventories. Correct rejected rows with small staging calls and finalize again. Never claim that partial staging means the phase has finished.

Use staged resources and task verdicts for this audit, then finalize the complete registry.
