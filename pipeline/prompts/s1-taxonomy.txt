# Stage 1 - Grow the task tree

You receive a mechanism card for every admitted task: its reviewed goal, observations, actions, success criteria, evaluation, input channels, interface route and published source-fact claims. Repeated evidence quotations, full interface documentation and reconstruction bookkeeping are kept in the saved specification rather than duplicated in the initial context. Source-fact claims describe the published task; the goal/actions/evaluation describe the reviewed selected protocol and may contain implementation choices. Use the published mechanics to establish the required capability. Organise these tasks into a tree of requirement domains and sub-classes: under `benchmarks`, every leaf is a sub-class whose parent is a domain (exactly two levels), and the number of domains and sub-classes is decided by the tasks themselves, not by a preset list. Names are aids, not the basis of the classification.

Use `read_task_details` only when a mechanic is ambiguous or a card field explicitly has `detailAvailable: true`. Read any such referenced field needed for classification before assigning that task. The tool reads one saved reviewed section without browsing or changing the task. Its text is paginated: follow `nextOffset` to obtain the rest of a needed section. Keep detail requests focused, reuse what you already read, and preserve the distinction between source facts and reconstruction decisions. A bounded supplemental context allowance prevents repeatedly loading the full library. The complete task ID inventory must remain covered; do not omit a task because its details are long.

The single `benchmarks` root holds both interactive tasks and fixed, published evaluations. Task kind describes the execution interface and does not determine its domain, leaf or train/unseen membership. All tasks have passed the shared no-audio-input scope gate. Every other input type, including text and video, is eligible. Reputation never substitutes for source-supported rules and an official scorer. No benchmark name, task family, child node or direction is prescribed.

Rules:
- Group by what the agent must do to succeed. Compare goals, the information available in observations, choices in the action space, feedback and the decisions required by the success condition. Do not classify by theme, institution, popularity, source family or data type alone.
- Leaves are directions (sub-classes). Every task goes to exactly one leaf under the shared root. A node without tasks exists only as the parent of other nodes. A domain groups sub-classes that share a requirement family; a sub-class groups tasks whose success demands the same decisions.
- Preserve a meaningful direction even when it currently has one task. Never merge unrelated capabilities to satisfy a split quota. The host will request published tasks for directions that lack independent unseen or train tasks after the classification.
- Give every node a stable kebab-case id, a short label and a one-sentence definition that says what the agent must do.
- Include a boundary explaining which capabilities belong in each node and which nearest neighbouring capabilities do not. Include an assignment reason citing the reviewed task mechanics that justify each task's leaf membership. These are classification inferences, not new claims about the source.
- Use source-supported mechanics to identify the capability. Newly selected implementation details, such as logging format or reconstruction seeds, must not create artificial directions. An official or Real2Sim route alone is not a capability direction.
- Nothing is cross-listed: one task, one direction.

Finish with exactly one `submit_taxonomy` call. The host reports violations; fix them and submit again.
